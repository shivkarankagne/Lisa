# LISA — Completion Plan

**Date:** 2026-09-18
**Status:** Active plan
**Governing document:** LISA Master Engineering Brief for Astra
**Audience:** LISA engineering team and Astra
**Baseline commit:** `bf02a68`

This document defines what is left to build for LISA to be a fully working
product, in what order, and how each step is accepted. It does not replace
the Master Engineering Brief; it applies the brief to the current code and
records the decisions in §2.

---

## 0. Definition of "fully working"

LISA 1.0 is fully working when a user can:

1. Copy one `lisa` executable onto an Apple Silicon Mac.
2. Point it at a folder of documents (txt, md, pdf at minimum).
3. Have LISA ingest, chunk, embed, and store them persistently.
4. Ask a question in the built-in GUI, the CLI, or over HTTP.
5. Receive an answer generated by a local model, grounded in retrieved
   chunks, with citations to the source documents.
6. Restart the machine and do it again without re-ingesting.

With nothing else installed: no Python, Docker, database server, embedding
server, or LLM server. The only external inputs are the model files the
user chooses.

---

## 1. Goal and priorities

**Goal:** one native executable that does ingestion, storage, search,
context building, and local inference — faster and with fewer runtime
dependencies than any comparable stack.

Priorities, in order:

1. **Works end to end** (§0).
2. **Single executable.** `otool -L build/lisa` lists only macOS system
   libraries and frameworks.
3. **Fast.** Every hot path is benchmarked; the fastest correct option wins,
   regardless of who wrote it.
4. **Small.** Binary size is tracked per release. Components are chosen
   partly on footprint.
5. **Portable by design.** Only ARM64 macOS is built and optimised now, but
   every line is written so that other CPUs, operating systems, and GPUs
   are added later as new backends, not rewrites (§2a).

**Order of work:** build it → finish it → perfect it. First the working
product (§6), built on upgrade seams (§7). Then perfecting (§8).

## 1a. Market position

Researched 2026-09-18 from vendor documentation and third-party reviews
(sources at the end of this section). Vendor claims are unverified until
W0 measures them.

### Problem LISA solves

Organisations hold large amounts of private documents. Their people cannot
get answers out of them quickly, and they are not allowed (or not able) to
use cloud AI. Existing local options are either heavy server stacks or
hobbyist tools that are hard to approve, deploy offline, or audit.

**LISA in one sentence:** correct, sourced answers from private documents,
on machines that cannot touch the internet, in a form a security team can
approve — as one file, with no server stack.

### Gaps LISA targets

1. **Truly offline install.** Copy one file by USB and run. No container
   images, no install-time downloads.
2. **CPU-only / no server.** Runs well on a laptop or edge box without a GPU
   or data centre.
3. **Embeddable.** A C library other products can link. None of the above
   ships as a library.
4. **Small security review.** One binary with a short, recorded component
   list (§5 intake records → SBOM).
5. **Affordable for small organisations** that cannot buy enterprise
   platforms and cannot run server stacks.

### Where LISA does not compete (for now)

- Large enterprises buying on compliance certificates, integrations, and
  brand (Cohere, Glean, Zylon).
- Feature breadth (agents, many connectors). LISA wins on deployment,
  footprint, and trust, not on feature count.

### Consequences for this plan

- A **GUI is required** for non-technical users (§2 decision 14, W10).
- **Offline install** is a 1.0 exit criterion (W12).
- **CPU-only performance** (small quantised models, low RAM) matters more
  than retrieval kernel speed.
- **Citations and audit** move toward the front of the plan.
- **W0 competitive baseline** sets the numbers LISA 1.0 must beat.

## 2. Decisions

| # | Decision |
| :--- | :--- |
| 1 | **Reuse wherever possible.** Commodity functionality comes from mature open-source libraries. LISA builds only what no suitable library provides, or what LISA must control to be faster or better (§5). |
| 2 | **All permissive licenses are accepted:** MIT, BSD-2, BSD-3, ISC, Apache-2.0, zlib, public domain. Copyleft is rejected: GPL, AGPL, LGPL, SSPL, and dual GPL/commercial. |
| 3 | **Single executable is the requirement; language is not.** LISA's own code is C by default. C and C++ are acceptable inside the binary. OS frameworks (Accelerate, Metal) are allowed only as optional faster backends behind a LISA interface with a portable fallback — never as the only path (§2a). |
| 4 | **Storage is hybrid.** LISA owns a memory-mapped vector file. SQLite (linked in) stores metadata, provides the write-ahead log, transactions, locking, and FTS5 keyword search. |
| 5 | **No attachment to assembly.** Every compute kernel is chosen by benchmark: scalar C, compiler auto-vectorisation, NEON intrinsics, hand-written assembly, Apple Accelerate, or ggml. The fastest correct one ships. The others remain as test references. |
| 6 | **Third-party code is vendored** into `third_party/<name>/` at a pinned version. No git submodules, no package managers at build time. |
| 7 | **Build first.** Work is ordered by engineering dependency and correctness only. |
| 8 | **HTTP server: CivetWeb** (MIT, C, embeddable, statically linked), replacing the hand-written `src/api/http.c`. Chosen over cpp-httplib because LISA's own code is C, and CivetWeb already handles the multi-read header parsing, keep-alive, and threading that `http.c` lacks. |
| 9 | **Inference: llama.cpp / ggml**, vendored and statically linked behind LISA's own model and inference interfaces. It also provides the tokenizer, GGUF loading, quantisation, KV cache, Metal backend, and embedding models. |
| 10 | **Platform: ARM64 macOS first** (brief §7A). It is the only platform built, tested, and optimised for 1.0. Other platforms start after 1.0 meets its exit criteria. |
| 11 | **Portable by default.** Every component and every line of LISA code must be able to run on all future targets. Platform-specific code lives only behind the platform layer or the kernel registry (§2a). |
| 12 | **64-bit targets only.** No 32-bit support. |
| 13 | **Build system: CMake.** Replaces the Makefile. Required for Windows later and for vendoring llama.cpp now. |
| 14 | **GUI is part of 1.0.** A web UI (HTML/CSS/JS) is compiled into the binary and served by `lisa serve` on localhost. `lisa gui` opens it in a native window using the OS web view via **webview/webview** (MIT); if no web view is available, it opens the system browser. One codebase works on every platform. No Electron, no Node, no separate app at runtime. |

| 15 | **Open core.** The public GitHub repository (`Lisa`) is the free core under **Apache-2.0**. Paid enterprise features live in a separate private repository (`lisa-enterprise`) under a commercial license and plug in through the extension points in W3. The core never depends on enterprise code (§2b). |

## 2a. Portability readiness

These are built as part of the working product (§6), so that future platforms are additions
rather than rewrites. No non-ARM64 backend is written for 1.0.

| # | Requirement | Built now | Added later |
| :--- | :--- | :--- | :--- |
| P1 | **Platform layer** `src/platform/`: mmap, file locks, threads, time, paths, filesystem walk. All OS calls go through it. | POSIX implementation | Windows implementation |
| P2 | **Kernel registry**: table of function pointers (`l2`, `dot`, `topk`, …) selected once at startup by CPU feature detection. Callers never call a kernel directly. | Scalar + ARM64 NEON entries | x86 AVX2 / AVX-512, GPU entries |
| P3 | **NEON intrinsics preferred over raw assembly.** Intrinsics compile unchanged on macOS, Linux, and Windows ARM64. Assembly is kept only if the L1 shoot-out shows a measurable win, and then lives in a `.S` file with a symbol-naming macro (`_name` on Mach-O, `name` on ELF). | — | — |
| P4 | **64-bit sizes** (`int64_t`) for counts, dimensions, offsets, and IDs in the public API and all file formats. | Yes (W3) | — |
| P5 | **File formats:** little-endian stated in the spec, byte-order check on open, fixed-width types only, version field, alignment specified. | Yes (W2) | — |
| P6 | **Portable components only** in the reuse map. OS-specific libraries only as optional backends with a portable fallback. | Yes (§5) | — |
| P7 | **CMake** with per-platform source lists and feature options. | Yes (W1) | New toolchains |
| P8 | **Portability canary in CI:** build and test the scalar-only path on Linux x86-64 in addition to ARM64 macOS. This is test coverage, not an x86 backend. | Later (L8) | Full CI matrix |
| P9 | **No platform assumptions in LISA code:** no hard-coded `/` paths, no `long` for sizes, no reliance on `char` signedness, no unaligned access outside kernels. | Code review rule | — |

## 2b. Business model: open core

### Free — public repo, Apache-2.0

Everything a single user or a single machine needs:

- Single binary: ingest, storage, hybrid search, context engine, local
  inference, cited answers
- GUI, CLI, HTTP API, C library (`lisa.h`)
- All platforms as they are added
- Community support (GitHub issues)

### Paid — `lisa-enterprise`, commercial license

What organisations need to deploy LISA for many people under governance:

| Area | Features |
| :--- | :--- |
| Multi-user + identity | User accounts, admin console, LDAP / Active Directory, OIDC / SAML SSO |
| Permissions + audit | Permission-aware retrieval (answers only from documents the user may see), document-level ACLs, tamper-evident audit log, audit export (SIEM) |
| Security + compliance | Encryption at rest, signed builds + SBOM, air-gap update bundles, compliance documentation, certifications |
| Support + SLA | Support contracts, SLAs, deployment help, commercial SDK license with indemnity |

### Rules

1. **The free edition is complete and genuinely useful.** Enterprise adds
   governance for many users; it never removes or cripples single-user
   features.
2. **No enterprise code in the public repo.** The public repo contains only
   the extension points, with no-op default implementations.
3. **Extension points are public, stable API** (W3): auth provider,
   authorisation filter on retrieval, audit sink, storage encryption
   provider, admin API routes. They are tested in the core with no-op and
   test implementations.
4. **Contributions** to the public repo are accepted under a Contributor
   License Agreement (CLA) or Developer Certificate of Origin (DCO) that
   lets the company ship them in both editions. Decide which before the
   first outside contribution.
5. **Trademark.** "LISA" name and logo usage is governed by a trademark
   policy; Apache-2.0 does not grant trademark rights (§8 question 4).
6. **Build.** `lisa-enterprise` vendors the core at a pinned commit and
   builds the paid single binary with enterprise modules linked in.

### Consequences

- The repository stays **public**. It is not made private.
- The public repo gets: `CONTRIBUTING.md`, `CODE_OF_CONDUCT.md`,
  `SECURITY.md` (vulnerability reporting), issue templates.
- Public-repo CI on GitHub-hosted macOS ARM64 runners is free.

## 4. Known defects in existing code

Fix before building on top of the affected code. Ordered by severity.

### D1 — Assembly kernel ABI violation — HIGH — FIXED (W1)
`src/kernels/arm64/lisa_ultra_mac.s` receives `int n` and `int dim` in
`w2` / `w3` but uses the full 64-bit `x2` / `x3` (`cmp x9, x2`,
`lsl x16, x3, #2`, `mul x13, x9, x3`). AAPCS64 leaves the upper 32 bits of
32-bit arguments undefined. It works today by chance.

**Fix:** `sxtw x2, w2` and `sxtw x3, w3` at kernel entry, or change the
kernel contract to 64-bit sizes. Add a regression test.

### D2 — Whole dataset copied on every query — HIGH (performance) — FIXED (W1)
`lisa_search_exact_asm` in `src/kernels/arm64/lisa_asm_wrapper.c` copies
all `n * dim` floats into a padded buffer on every search (≈30 MB per query
at 10k × 768). The recorded 1.644 ms includes this copy.

**Fix:** handle the `dim % 4` tail inside the kernel, or store vectors
pre-padded. Remove the per-query copy. Re-benchmark.

### D3 — `-O0` product build — HIGH — FIXED (W1)
The Makefile builds at `-O0` because `-O2` "miscompiled comparison logic in
test code". Undefined behaviour in the test code is the likely cause.

**Fix:** build tests with `-O2 -fsanitize=undefined,address`, fix any UB,
move the product build to `-O2`. All benchmarks use product flags.

### D4 — Storage delete shifts indices — MEDIUM — FIXED (W2, storage v2)
`storage_delete` renumbers every later vector. Stored references break.
**Fix:** stable IDs (W2).

### D5 — HTTP re-reads the collection per request — MEDIUM
`src/api/http.c` calls `storage_open` / `storage_close` per `/search`.
**Fix:** resolved by W9 (collections opened once at server start).

### D6 — HTTP accepts arbitrary filesystem paths — MEDIUM (security)
`?collection=<path>` is used directly as a path.
**Fix:** resolved by W9 (data root + validated collection names).

### D7 — HTTP parses headers with a single `recv` — LOW
**Fix:** resolved by W9 (CivetWeb replaces `http.c`).

### D8 — Build and test hygiene — LOW — FIXED (W1)
- `make test` runs prebuilt test binaries; it does not rebuild them.
- `test_storage_mutation` and `tests/test_api.sh` are not in `make test`.
- `src/kernels/arm64/lisa.s` is an empty tracked file.
- `lisa_search_exact_asm` is declared with `extern` in `main.c` and
  `http.c` instead of in a header.
- No CI.

**Fix:** Makefile builds all tests from source; `make test` runs all of
them including ASan variants; delete `lisa.s`; header for the asm entry
point; GitHub Actions on `macos-14` (ARM64).

### Acceptance criteria

**W1 — Build foundation**
- `cmake --build` produces `build/lisa`; `ctest` builds every test from
  source and runs all of them, including ASan/UBSan variants.
- Product built at `-O2`. D1 fixed (or the assembly kernel replaced by NEON
  intrinsics). D2 fixed: no per-query copy of the dataset.
- All OS calls (files, mmap, locks, threads, time) go through
  `src/platform/`.
- Kernels are called only through the registry.

**W2 — Storage v2**
- Collection directory: `vectors.<gen>.lisa` (mmap'd via the platform
  layer, little-endian, versioned 64-byte header, packed rows) +
  `meta.sqlite` (SQLite, WAL mode). Spec: `docs/formats/collection-v2.md`.
  *As built:* the generation number in the file name makes compaction an
  atomic switch; rows are packed (64-byte aligned when `dim % 16 == 0`)
  because NEON loads need no alignment and packing avoids a stride
  parameter in every kernel.
- Stable `uint64` IDs. Delete never renumbers; tombstones + compaction.
- Metadata per chunk, at least: `doc_id`, `chunk_id`, `source_path`,
  `offset`, `length`, `text`, `content_hash`.
- Collection header records embedding model ID, dimension, and format
  version. Opening with a different embedding model fails with a clear
  error.
- Crash at any point leaves the collection at the last committed state
  (kill-during-write test).
- One writer, many readers. A second writer waits or fails cleanly.
- v1 / v1.1 collections migrate with one call (`lisa_store_migrate_v1`);
  the `lisa migrate` CLI command is added with the other commands in W9.

**W3 — Public API**
- `include/lisa.h` is the only public header. Opaque handles. Ownership
  and lifetime documented per function. Error codes enumerated.
- All sizes, counts, IDs are `int64_t`.
- API version macro; semantic versioning (§7).
- Extension points defined, documented, and tested with no-op
  implementations: `lisa_auth_provider`, `lisa_retrieval_filter`,
  `lisa_audit_sink`, `lisa_storage_crypto`, `lisa_http_routes`.
- CLI, HTTP, and GUI use only this API. *As built:* met when W9 replaces
  the current CLI and HTTP server; the GUI uses the W9 HTTP API.

**W4 — Models**
- Default generation model and embedding model chosen; both licenses
  permit commercial redistribution; recorded in intake records.
- Output matches upstream llama.cpp for fixed seed and greedy decoding.
- Metal enabled through ggml; CPU path works without Metal.
- Other ggml backends disabled but not removed.
- `lisa model` shows the configured model and verifies the file
  (size + hash).
- **Initial targets (confirm by measurement):** Apple Silicon M1 or newer,
  8 GB RAM; first answer token ≤ 5 s on 8 GB; collections up to 5,000
  documents. Measured numbers recorded in a report.

**W5 — Documents**
- txt, md, pdf. Each format is one extractor registered by file type.
- Output: normalised UTF-8 text + source offsets (page number for PDF).
- Chunker: configurable size and overlap; respects paragraphs.
- PDFium links statically into the single binary (verified before any
  other W5 work; fallback: build PDFium from source).

**W6 — Ingest**
- `lisa ingest <folder>` run twice on an unchanged folder does nothing.
- Edited file → old chunks removed, new chunks added. Deleted file → its
  chunks removed.
- Ingest runs as a background job with an ID and progress; `ask` works
  during ingest.

**W7 — Retrieval**
- Exact vector search via the kernel registry.
- FTS5 index in the collection's SQLite file.
- Reciprocal rank fusion, weights configurable.
- Metadata filter hook (used by enterprise `lisa_retrieval_filter`).
- Implemented behind `lisa_index`; exact search is the first
  implementation.

**W8 — Context + answer**
- Pipeline of named stages: retrieve → filter → rank → dedupe → budget →
  generate. Stages can be added without changing callers.
- Every answer lists citations: document, page/offset, quoted passage.
- If no chunk passes a relevance threshold, the answer says so instead of
  guessing.
- The ask API takes a list of messages (one message in 1.0), so
  follow-up chat can be added later without an API change.
- Tokens stream to CLI, HTTP, and GUI.

**W9 — Interfaces**

CLI:

    lisa ingest  --data <dir> --collection <name> <path>...
    lisa search  --data <dir> --collection <name> --query "<text>" [--topk N]
    lisa ask     --data <dir> --collection <name> "<question>"
    lisa serve   --data <dir> [--port <port>]
    lisa gui     --data <dir>
    lisa model   [--set <path>]
    lisa migrate --from <v1-dir> --to <dir>
    lisa --version

HTTP (JSON, versioned):

    GET  /v1/health
    GET  /v1/collections
    POST /v1/collections/{name}/ingest
    GET  /v1/jobs/{id}
    POST /v1/collections/{name}/search   {"query": "...", "topk": 5}
    POST /v1/collections/{name}/ask      {"messages": [{"role": "user", "content": "..."}]}

- Binds to 127.0.0.1 only.
- Rejects requests whose `Host` or `Origin` is not the local server
  (blocks DNS rebinding and cross-site requests from web pages).
- Requires a per-session token, generated at start and handed to the GUI.
- Collection names validated (`[a-zA-Z0-9_-]+`), resolved under `--data`.
- Collections opened once and cached.

**W10 — GUI**
- Screens: collections; add folder (drag and drop) with progress; ask box;
  streamed answer with clickable citations showing the source passage;
  settings (model, data directory).
- Uses only the W9 HTTP API.
- All assets compiled into the binary; no requests to external hosts.
- `lisa gui` opens a native window; falls back to the system browser.
- Keyboard-only use; readable at 200% zoom; light and dark themes.
- Adds ≤ 5 MB to the binary (recorded).

**W11 — Release**
- Semantic version in binary, API, and file formats.
- macOS binary signed with a Developer ID and notarized, so it runs after
  download without security warnings.
- SHA-256 checksums published with each release.
- Config file (`lisa.toml` or JSON) with a version field; log file with
  levels.
- README quickstart: download, get a model, ingest, ask — in under five
  minutes.
- No telemetry. LISA makes no network connections except the local server.

**W12 — Validation (1.0 exit criteria)**
- Eval set ≥ 50 questions over a fixed public corpus (seeded by W0).
  Retrieval recall@k and citation accuracy recorded in a report.
- Clean-machine test: fresh macOS user account, copy binary + model, run
  §0 steps 1–6 through the GUI and the CLI.
- Offline test: Wi-Fi off from first copy to first answer.
- Crash-recovery test passes.
- 8-hour soak test on `serve`: no memory growth, no crashes.
- Matches or beats W0 on install time, offline operation, disk, and RAM;
  matches it on answer and citation quality.
- Binary size and `otool -L` output recorded.

## 7. Upgrade scope

Everything in §8 must be addable **without rewriting** the working product.
That is guaranteed by the seams below, which are built as part of §6 even
though only their first implementation exists in 1.0.

### Seams

| Future capability (§8) | Seam built into the working product | Built in |
| :--- | :--- | :--- |
| Faster kernels, multithreading, Metal / AVX / CUDA search | Kernel registry | W1 |
| Linux, Windows, other CPUs | Platform layer; CMake per-platform sources; portable components; `int64_t`; little-endian versioned formats | W1, W2 |
| Approximate index for large corpora | `lisa_index` interface (exact is first implementation) | W7 |
| Reranking, query rewriting, better dedupe | Context engine as a pipeline of named stages | W8 |
| Follow-up chat | Ask API takes a list of messages | W8, W9 |
| Citation verification | Citations carry document ID, offsets, and text hash | W2, W8 |
| New document formats, OCR | Extractor registry by file type | W5 |
| Swapping embedding models, re-index | Embedding model ID + dimension stored per collection | W2, W4 |
| Model catalog / downloads | Models referenced by ID in config; `lisa model` command | W4, W9 |
| Multilingual (incl. Indian languages) | Tokenizer and model configurable per collection | W2, W7 |
| Multi-user, concurrency | One writer / many readers; background jobs with IDs | W2, W6, W9 |
| TLS, auth, enterprise features | Extension points; HTTP middleware hook | W3, W9 |
| SDKs (Python, others) | Stable C API with opaque handles | W3 |
| Agents / tools | Generation API independent of the RAG loop | W4 |

### Upgrade rules

1. **Semantic versioning** for the binary, the C API, the HTTP API
   (`/v1`), and every file format.
2. **Additive within a major version.** New functions, fields, routes, and
   stages may be added; existing ones do not change meaning.
3. **Data always upgrades.** Version N+1 opens version N data, migrating
   automatically after making a backup. Every persistent file and the
   config file carry a version field.
4. **Deprecate before removing.** A feature is marked deprecated for at
   least one minor release before removal in the next major version.
5. **New features plug into seams.** If a new feature needs a seam changed,
   that change gets a design review and an API version bump.
